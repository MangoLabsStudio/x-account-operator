# 多人设内容系统：常驻编辑流水线契约

## 1. 背景

系统运营 10 个不同的中文 Crypto KOL 人设。目标不是让十个账号换头像复述同一份日报，而是让每个人设像真实的人一样，基于共同的市场信息形成不同注意力、不同判断和不同表达。

当前系统已经具备：

- 每日母帖池抓取与增量更新；
- 事实候选、观点候选和热点聚类；
- 选题历史与去重；
- 人设资料、口风和连续性；
- 自动生成待审核草稿；
- 人工审核，不自动发布。

现在需要解决的不是“几点发哪个栏目”，而是：怎样让每个人设在足够新的、已经确认的市场 Context 下，自然决定自己是否有值得说的内容。

## 2. 核心目标

每个人设应该：

- 有长期关注方向、认知边界和表达习惯；
- 每天关注和发布的内容可以完全不同；
- 同一个热点可以形成不同角度，但不能生成十条同构文案；
- 不必每天围绕热点，也不必固定发布某几类内容；
- 没有任何日更数量、固定栏目或轮转题目配额；
- 没有值得说的内容时允许少发或不发，不能为了数量制造常识、鸡汤或重复观点。

人设稳定性应体现在“他会关注什么、怎么看、怎么说”，而不是“每天必须发哪几类内容”。当天输出 0 条是合法结果。

## 3. 内容来源

系统可从下列来源自由获得灵感，但这些来源不能变成固定栏目或轮换表：

- 母帖池当天讨论最多的事实和观点；
- 交易机会、理财活动、空投、Meme 和链上机会；
- 行业分析、项目研究和商业模式判断；
- 市场情绪、人物评价、圈内争议和乐子；
- 交易过程中的具体感受、财富观和交易哲学；
- 利弗莫尔、巴菲特、芒格、索罗斯、霍华德·马克斯、塔勒布等人的公开方法论；
- 与人设身份和生活经验相符的小观察。

名人内容只有拿到可核验原文和出处时才能使用直接引语；否则只能转述公开方法论，不能制造名人语录。

## 4. 合格内容标准

一条候选内容至少应该：

- 有一个明确主题；
- 有该人设自己的判断或表达目的；
- 不是圈内读者无需当天材料就能回答的常识；
- 不是历史内容换标题重发；
- 不是为了安全而堆叠风险提示；
- 不是写了很多但没有当前结论；
- 有必要的信息量，但不写成研报、操作手册或百科；
- 不编造价格、数据、持仓、亲历、收益或人物引语；
- 读起来像人在说话，而不是 AI 汇总材料。

赚钱或机会内容应该说明大致如何参与、如何判断值不值得做、需要计算什么，不必替读者算完全部路径。

哲学、人物或乐子内容可以不提供赚钱方案，但必须有一句值得讨论或转发的表达，不能只是永远正确的万能鸡汤。

## 5. 人设差异

人设差异不能只体现在语气词。系统选题时还需要考虑：

- 他通常会注意什么；
- 什么事情会让他产生表达欲；
- 他习惯从哪个角度理解；
- 他愿意把问题讲到多深；
- 他以前表达过什么；
- 哪些主张符合或超出他的身份和认知边界。

同一份公共市场信息进入十个人设后，可以没人采用、只有一人采用，也可以多人采用。多人采用时，核心主张必须不同。

## 6. 已知痛点

### 6.1 市场 Context 不足

模型不知道市场最近真正发生了什么，导致内容像不熟悉 Crypto 的人硬写 Crypto。热点事实、市场背景和当前分歧必须先形成足够 Context，再进入选题和写作。

### 6.2 选题没有读者价值

系统曾选择冷门技术提案、显而易见的基础概念、已经讲过的 Builder Codes，或者读者不关心的权利边界。

### 6.3 内容过度谨慎

正文经常用“继续观察”“等待后续材料”“暂时没有交易条件”代替判断，风险提示反而挤掉读者真正关心的结论。

### 6.4 没有明确结论

一篇内容写了很多段，读者仍不知道作者到底怎么看、这件事意味着什么，或者在什么条件下值得参与。

### 6.5 过度过滤

为了避免常识和重复，系统又把当天题单过滤到只剩 4 个，导致内容供给不足。正确去重单位应是核心主张，而不是整个事件、项目或币种。

### 6.6 过度结构化

解决供给不足时，系统容易走向“每天两条热点、一条名人语录、一条交易哲学”的栏目排班。这会让账号失去真人感。

### 6.7 完全自由也会失控

“想到什么发什么”如果没有质量边界，模型可能随机发挥、重复旧话、写万能鸡汤，或者让十个人设重新变得一样。

### 6.8 人设尚未真正参与选题

当前路径更接近“先产生公共选题，再轮流分给人设”。真实顺序还需要回答：为什么这个人此刻会注意到它，并且真的有话想说？

## 7. 常驻编辑流水线

- 稳定产出与不为数量硬凑之间的矛盾；
- 允许经典交易哲学与避免常识语录号之间的矛盾；
- 自然表达与可重复质量控制之间的矛盾；
- 紧跟热点与避免全员追同一个热点之间的矛盾；
- 提供赚钱价值与避免全部内容项目化之间的矛盾；
- 共享事实 Context 与维持人设差异之间的矛盾。

调度器不直接规定内容类别，也不为了刷新而生成草稿。它只在下列时机重新评估“这个人设现在是否有值得表达的想法”：

1. 早间母池 Context 被人工审核并正式保存；
2. 同日有实质变化，并以新的正式输入 fingerprint 保存。

每一次评估按如下顺序执行：

1. **Context**：母池事实、作者观点、讨论热度、已验证补充和当前分歧形成候选输入；未正式保存的 Context 不得进入写作。
2. **Persona decision**：每个人设独立判断 Notice、Authority、Tension、Claim 和 Marginal value：他会不会注意到、能否在认知边界内发言、是否有矛盾或表达欲、能否给出非显而易见的主张、相对本人和团队近期内容是否有新增价值。
3. **Outcome**：结果只能是 `WRITE`、`HOLD` 或 `IGNORE`。`HOLD` 是内部未解问题或等待材料，不能被转换成“继续观察”“暂时不做”等填充正文；`IGNORE` 不生成内容；只有 `WRITE` 可进入下一步。
4. **Claim arbitration**：跨人设比较核心主张。同一事件但核心问题或结论不同可以共存；若只是同一主张换了人设口吻，只保留最自然的一位，其他人改为非写作结果。
5. **Draft and review**：只为仲裁后保留的 `WRITE` 生成候选稿，交给人工审核。候选稿不等于发布，也不触发任何 X 账号操作。

同一人设在同日可以因新的 material change 出现第二个候选，但不存在最低条数、最大填充数或按题目轮转。数量只反映有多少独立而有增量的 `WRITE`。

### 7.1 最小持久状态

- **Persona Card**：关注范围、惯性问题、证据偏好、认知边界、行动倾向和禁止主张；
- **Claim Memory**：主题、核心主张、证据、反证或失效条件、人设、日期和状态，防止跨天重说；
- **Open Loops**：尚未解决的问题、等待的数据和被挑战的旧结论；
- **Daily Editorial State**：正式 Context fingerprint、触发类型、每个人设的 `WRITE/HOLD/IGNORE`、理由与候选稿关联。

## 8. 可测试的实现契约

- 未正式批准的 Context 不创建人设评估或候选稿；
- 同一个正式输入 fingerprint 至多完成一次评估，重启服务不重复生成；
- 新 fingerprint 才允许同日增量评估；
- 每个人设都持久化一个明确结果，`HOLD/IGNORE` 不创建候选稿；
- 同一核心主张不能以不同口吻进入多个候选稿；不同核心主张可以引用同一事件；
- 允许整次运行没有任何 `WRITE`；
- `WRITE` 生成的是人工待审稿，系统不发布、不排期、不互动；
- 人设卡和历史主张必须影响评估，不能先产生公共题目再按名单轮流分配。

## 9. 验收重点

- 草稿可发布率和人工大改率，而不是每日草稿数；
- 人设辨识度，以及跨人设核心主张重复率；
- 低价值候选被人工否决的比例；
- `WRITE/HOLD/IGNORE` 的分布是否反映真实市场变化，而非凑数；
- material change 是否只带来增量候选，未变化时是否保持静默。

## 10. 硬边界

- 不自动发布、点赞、转发、关注或操作 X 账号；
- 不修改人设设定和已确认发布状态；
- 不制造交易、持仓、收益、生活经历或名人引语；
- 不把观点写成事实；
- 不为了任何数量目标强制生成低价值内容；
- 不用固定栏目、固定比例或机械轮播模拟真人；
- 不部署、不重启、不改生产配置。

## 11. 非目标

- 不把 `HOLD` 写成面向读者的保守废话；
- 不把人设数量误当作应生成的稿件数量；
- 不以固定比例安排热点、机会、哲学或人物内容；
- 不用历史语录、常识或无来源的“交易哲学”填充空档。
